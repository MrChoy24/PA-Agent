## 一、部署前先想清楚三件事

### 1. 这台服务器要做什么

| 角色 | 需要的东西 |
| --- | --- |
| **只分析、不下单**（推荐先这样跑一周） | AI Key + 行情网络 |
| **真实下单** | 上面 + 交易所 API Key（要开交易权限 + IP 白名单） |

**默认配置就是「只分析」**：包里的 `settings.json` 首启自动生成时，`auto_trade.enabled=false`、`dry_run=true`。不填交易所 Key 也完全能跑。

### 2. 交易所网络

服务器必须能访问 `www.okx.com`（或 `api.binance.com`）。国内服务器**大概率不通**，需要代理，见[第四节](#四先确认服务器能不能访问交易所)。

### 3. AI 模型的成本

每次分析要发两轮大 prompt（Stage1 约 95K tokens、Stage2 约 74K）。15 分钟周期一天约 96 次分析，**用 glm-5 一天成本大约几块钱**。建议先用 `PA_DAEMON_ANALYSIS_COOLDOWN=300`（5 分钟）控制频率。

## 二、服务器准备

### 2.1 硬件

实测资源占用：

| 项目 | 数值 |
| --- | --- |
| 常驻内存（RSS） | 约 38 MB |
| 峰值内存（一次分析） | 约 120 MB |
| 磁盘 | 镜像约 260 MB + 日志/记录按月增长 |

**1 核 1G 就够**，2G 更稳（构建镜像时 pip 装依赖会短暂吃内存）。

### 2.2 软件

```bash
# 确认 Docker 已装（1Panel 自带）
docker --version
docker compose version      # 需要 v2，输出 Docker Compose version v2.x.x

# 如果只有 docker-compose（v1，带横杠），把下文所有
#   docker compose
# 换成
#   docker-compose
```

### 2.3 目录规划

**固定用 `/opt/pa-agent`，不要改**。原因：`docker-compose.1panel.yml` 里所有路径都写死了绝对路径 `/opt/pa-agent`（为了绕开 1Panel 把编排文件存到自己目录导致相对路径全错位的问题）。换路径就必须改编排文件里 8 处路径。

```bash
sudo mkdir -p /opt/pa-agent
```

## 三、上传并解压

### 3.1 上传

要上传的文件是 **`PA_Agent-server.beta.tar.gz`**（公开发布版）。三种方式任选：

```bash
# 方式一：本机执行（推荐，最快）
scp PA_Agent-server.beta.tar.gz root@你的服务器IP:/opt/pa-agent/

# 方式二：1Panel 面板 → 文件 → 上传到 /opt/pa-agent

# 方式三：服务器上直接从 GitHub Releases 拉（不用本机中转）
cd /opt/pa-agent
wget https://github.com/MrChoy24/PA-Agent/releases/download/v0.1.0/PA_Agent-server.beta.tar.gz
```

> 文件名说明：服务端包有两种，内容相同，只是打包时的顶层目录名不同。
>
> | 文件 | 来源 | 顶层目录 |
> | --- | --- | --- |
> | `PA_Agent-server.beta.tar.gz` | GitHub Releases（**推荐**） | `PA_Agent-server.beta/` |
> | `PA_Agent-server.tar.gz` | 自己在本地 `.pipwork/build_all.py` 构建 | `PA_Agent-server/` |
>
> 两种都靠 `--strip-components=1` 把顶层目录剥掉，所以**解压命令对两者完全一样**，只改文件名即可。
> Releases 页面：<https://github.com/MrChoy24/PA-Agent/releases>

### 3.2 解压

```bash
cd /opt/pa-agent
sudo tar -xzf PA_Agent-server.beta.tar.gz --strip-components=1
sudo rm PA_Agent-server.beta.tar.gz

# 确认结构正确
ls
```

应该看到：

```
Dockerfile            docker-compose.1panel.yml   pyproject.toml
LICENSE               docs/                       requirements-daemon.txt
PA_Agent使用文档.md    experience/                 run.py
README.md             pa_agent/                   .env.example
config/               deploy/                     .dockerignore
docker-compose.yml    prompt_engineering/         tests/
```

> **`--strip-components=1` 不能漏**。包内顶层还有一个目录（`PA_Agent-server.beta/` 或
> `PA_Agent-server/`），漏了就变成 `/opt/pa-agent/PA_Agent-server.beta/Dockerfile`，
> 而 `build.context: /opt/pa-agent` 在根目录找不到 Dockerfile，构建直接报 `failed to read dockerfile`。

### 3.3 包里有 / 没有的东西

| 有 | 没有（必须自己建） |
| --- | --- |
| `config/settings.example.json`（样例） | **`config/settings.json`（首启自动生成）** |
| `.env.example`（样例） | **`.env`（必须手工建）** |
| `Dockerfile`、两个 compose 文件 | 交易所 API Key |
| `deploy/docker-entrypoint.sh` | AI API Key |

**两个关键认知**：

- `settings.json` 不用手建 —— 首次启动时 `DaemonConfig.from_env()` 会自动写一份默认值。
- `.env` **必须**手工建 —— 没有它，容器里 AI Key 为空，分析会直接失败。

## 四、先确认服务器能不能访问交易所

**这一步跳过会浪费你半小时**。在国内服务器上，OKX 与 Binance 大概率不通。

### 4.1 直接测

```bash
curl -s -o /dev/null -w "OKX: %{http_code} (%{time_total}s)\n" --max-time 10 \
    https://www.okx.com/api/v5/public/time
curl -s -o /dev/null -w "Binance: %{http_code} (%{time_total}s)\n" --max-time 10 \
    https://api.binance.com/api/v3/time
```

- 两个都返回 `200` → 直连没问题，**跳过 4.2**。
- 超时 / 报 `Could not resolve host` / 返回 `000` → 需要代理，继续看 4.2。

### 4.2 配代理

**情形 A：代理跑在服务器本机**（ShellCrash / Clash / v2ray 装在服务器上）

容器里的 `127.0.0.1` 是容器自己，写它一定不通。要用 `host.docker.internal`：

```bash
# 1) 先确认宿主机代理端口在监听
ss -lntp | grep 7890

# 2) 确认 allow-lan 开着（ShellCrash：2-功能设置 → 1-HTTP/SOCKS5 代理 → 允许局域网连接）
#    否则容器从 172.x 网段访问会被拒

# 3) 写进 .env（第五节会详细讲怎么建）
#    HTTPS_PROXY=http://host.docker.internal:7890
#    HTTP_PROXY=http://host.docker.internal:7890
```

`docker-compose.1panel.yml` 里已经配好 `extra_hosts: ["host.docker.internal:host-gateway"]`，不用改。

**情形 B：代理在别的机器**（路由器 / NAS / 另一台内网机）

直接写内网 IP：

```
HTTPS_PROXY=http://192.168.1.10:7890
HTTP_PROXY=http://192.168.1.10:7890
```

**两种情形都建议加 `NO_PROXY`**，让钉钉、AI 网关走直连，避免绕远和 SSL 报错：

```
NO_PROXY=oapi.dingtalk.com,www.pushplus.plus,api.deepseek.com,open.bigmodel.cn,api.openai.com,generativelanguage.googleapis.com,api.moonshot.cn,dashscope.aliyuncs.com
```

### 4.3 容器内验证（启动后做）

```bash
docker exec pa-agent sh -c 'env | grep -i proxy'
docker exec pa-agent python -c "
import httpx
print(httpx.get('https://www.okx.com/api/v5/public/time', timeout=15).status_code)
"
```

## 五、建 .env（最关键的一步）

`.env` 里是**明文密钥**，所以它不在包里、也不会被任何构建脚本带上服务器。

### 5.1 从样例复制

```bash
cd /opt/pa-agent
sudo cp .env.example .env
sudo chmod 600 .env          # 只有 root 能读
sudo vi .env
```

### 5.2 最小可用配置（只分析、不下单）

**只改这 4 行就能跑起来**：

```bash
# ── AI 模型（必填）──
PA_AGENT_API_KEY=你的Key
PA_AGENT_API_BASE=https://open.bigmodel.cn/api/paas/v4
PA_AGENT_MODEL=glm-5

# ── 盯盘对象 ──
PA_DAEMON_SYMBOL=BTCUSDT
```

其他全部保持样例里的默认值即可。

> ⚠️ **不要把 `PA_AGENT_MODEL` 改成 `glm-4-flash`**。那个模型名会触发「精简契约」
> （stage1 本地伪造、stage2 只解析 3 个字段），导致 `trade_confidence` 恒为 50，
> 自动下单永远被 `min_confidence` 拦死。想省钱请降频，不要换小模型。

### 5.3 AI 服务商对照表

PA Agent 走的是 **OpenAI 兼容协议**（`POST {base_url}/chat/completions`），
所以只要服务商提供 OpenAI 兼容端点，填上 `base_url` 与模型名就能用。
下表是几家主流服务商，`base_url` 与模型名均已按其官方文档核对：

| 服务商 | 官方文档 | `PA_AGENT_API_BASE` | `PA_AGENT_MODEL`（示例） |
| --- | --- | --- | --- |
| 智谱 BigModel | <https://docs.bigmodel.cn/> | `https://open.bigmodel.cn/api/paas/v4` | `glm-5`（也可 `glm-5.3`） |
| DeepSeek 官方 | <https://api-docs.deepseek.com/> | `https://api.deepseek.com` | `deepseek-flash` |
| OpenAI | <https://platform.openai.com/docs> | `https://api.openai.com/v1` | `gpt-4o` |
| Google Gemini | <https://ai.google.dev/gemini-api/docs> | `https://generativelanguage.googleapis.com/v1beta/openai` | `gemini-2.5-flash` |
| Moonshot Kimi | <https://platform.kimi.com/docs> | `https://api.moonshot.cn/v1` | `kimi-k3.1-pro` |
| 阿里云百炼（千问） | <https://help.aliyun.com/zh/model-studio/> | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` |
| 硅基流动 SiliconFlow | <https://docs.siliconflow.cn/> | `https://api.siliconflow.cn/v1` | `deepseek-ai/DeepSeek-V3` |
| 火山方舟 | <https://www.volcengine.com/docs/82379> | `https://ark.cn-beijing.volces.com/api/v3` | 你的推理接入点 ID |

Key 申请入口通常在对应控制台（如智谱 <https://bigmodel.cn/usercenter/proj-mgmt/apikeys>、
DeepSeek <https://platform.deepseek.com/api_keys>）。

> ⚠️ **注意三点**
>
> 1. **模型名以你账户里实际可用的为准**。上表只是各家的常见示例，服务商会改名、下线旧模型；
>    填错会直接报 `model not found`（HTTP 404）。拿不准就在该服务商控制台的模型列表里查。
> 2. **Anthropic Claude 的原生协议（`api.anthropic.com`）不是 OpenAI 兼容的**，直接填进来会 400。
>    要用 Claude，走提供 OpenAI 兼容转发的网关，不要填 Anthropic 官方域名。
> 3. **`base_url` 末尾不要带 `/chat/completions`**，程序会自己拼。带上了会变成
>    `.../chat/completions/chat/completions` 报 404。

**备用链路池**（主通道挂了自动按顺序切换，改了立即生效、不用重建镜像）：

```bash
PA_AGENT_FALLBACKS=名称|模型|地址|Key;名称|模型|地址|Key
```

举例（两个不同网关，Key 各不相同，就要分别写全）：

```bash
PA_AGENT_FALLBACKS=备用A|glm-5|https://open.bigmodel.cn/api/paas/v4|你的另一个Key;备用B|deepseek-flash|https://api.deepseek.com|另一个Key
```

Key 位置写 `-` 表示复用 `PA_AGENT_API_KEY`（同一个网关只是换模型时最省事）。
写这一行就**整段替换** `settings.json` 里的备用池；不写则沿用文件里的。

### 5.4 钉钉通知（可选）

```bash
DINGTALK_WEBHOOK_URL=https://oapi.dingtalk.com/robot/send?access_token=xxx
DINGTALK_SECRET=SECxxxxxxxx
```

钉钉群机器人 → 安全设置选「**加签**」→ 把密钥填进 `DINGTALK_SECRET`。

**填了这两项就等于启用钉钉**，即使 `settings.json` 里 `dingtalk.enabled=false`。
实盘成交后会自动推送一条成交回报（含成交均价 / 数量 / 名义金额与保证金 / 下单时间 / 委托号 / 止损与止盈挂单结果），默认就发。

### 5.5 交易所凭据（只有要下单才需要）

**Binance**：

```bash
BINANCE_API_KEY=xxx
BINANCE_API_SECRET=xxx
BINANCE_TESTNET=false          # 先用 true 测
```

API 管理里要勾「允许现货交易」；做合约还要勾「允许合约交易」。
**把服务器公网 IP 填进 Key 的 IP 白名单**，否则报 `-2015 Invalid API-key, IP, or permissions`。

**OKX**：

```bash
OKX_API_KEY=xxx
OKX_API_SECRET=xxx
OKX_PASSPHRASE=xxx             # OKX 特有，必填
OKX_DEMO=false                 # 先用 true 测模拟盘
```

API 管理里权限选「交易」，同样要配 IP 白名单。

> ⚠️ 实盘 Key 配 `OKX_DEMO=true` 会报 `50101 APIKey does not match current environment`。
> 模拟盘需要**单独申请一套 Key**，两者不能混用。

### 5.6 自动交易开关（默认全关）

```bash
PA_DAEMON_AUTO_TRADE=false     # 总开关
PA_DAEMON_DRY_RUN=true         # true = 只记录意图，不发单
PA_DAEMON_VENUE=binance        # 在哪个所下单（可以和行情来源不同）
```

### 5.7 下单金额怎么算（**没有「按余额百分比」模式**）

一律是**固定金额**，与账户余额无关。由 `PA_DAEMON_MARGIN_MODE` 二选一：

| 模式 | 名义金额 | 占用保证金 | 哪个变量生效 |
| --- | --- | --- | --- |
| `cross`（全仓） | `PA_DAEMON_MAX_NOTIONAL` | 名义 ÷ 杠杆 | `MAX_NOTIONAL` |
| `isolated`（逐仓） | `MARGIN_PER_TRADE × LEVERAGE` | `MARGIN_PER_TRADE` | `MARGIN_PER_TRADE` |

**重要**：2026-11-14 之后，`isolated` 模式下名义金额**仍然受 `MAX_NOTIONAL` 封顶**。
以前是「保证金 × 杠杆，不被上限收敛」，导致面板写 15 U 却能开出 12500 U。现在超上限会收敛并打警告。

金额对照（全仓 10 倍 + ETH 约 2000 U）：

| MAX_NOTIONAL | 名义金额 | 占用保证金 | ETH 张数 |
| --- | --- | --- | --- |
| 15 U | 15 U | 1.50 U | 0.07 |
| 50 U | 50 U | 5.00 U | 0.25 |
| 200 U | 200 U | 20.00 U | 1.00 |

张数按 `lotSz`（OKX 常见 0.01 张）**向下取整**，所以实际成交名义会略低于设定值，这是正常的。

### 5.8 五个「没有环境变量通道」的风控项

以下五项**只能改 `config/settings.json`**，`.env` 里写什么都没用：

| 项 | 含义 |
| --- | --- |
| `min_confidence` | 自动下单最低置信度（默认 60） |
| `max_daily_orders` | 每日最大下单数（默认 10） |
| `require_stop_loss` | 必须带止损才下单（默认 true） |
| `allowed_symbols` | 品种白名单（默认空 = 不限） |
| `max_price_deviation_pct` | 跨所价差护栏（默认 0.3%） |

这样设计是为了避免「`.env` 里一个拼写错误就把风控放宽了」。
好在 `settings.json` 支持**热重载** —— 改完立刻生效，不用重启容器（见 9.3）。

## 六、构建镜像并启动

### 6.1 必须用命令行，不要在 1Panel 面板点「启动」

```bash
cd /opt/pa-agent
sudo docker compose -f docker-compose.1panel.yml up -d --build
```

**为什么不能直接点面板**：compose 里写的是 `image: pa-agent:latest`，这个镜像**不存在于 Docker Hub**，是本地 build 出来的。1Panel 的「创建编排」会先去 registry 拉它，于是报：

```
failed to resolve reference "docker.io/library/pa-agent:latest" ... i/o timeout
```

这不是网络问题（Docker Hub 上根本没这个镜像，配加速器也没用）。命令行 `--build` 会先 build 再起容器，完全不碰 registry。

### 6.2 构建过程会做什么

```
[+] Building 120.5s
 ├─ 拉基础镜像 python:3.12-slim        （拉不动见 6.3）
 ├─ apt-get install ca-certificates tzdata util-linux
 ├─ pip install -r requirements-daemon.txt   （走清华源）
 ├─ COPY pa_agent / prompt_engineering / experience
 └─ 建运行时目录、装入口脚本
[+] Running 2/2
 ✔ Network pa-agent_default  Created
 ✔ Container pa-agent        Started
```

**耗时**：正常 2~4 分钟。第一次拉基础镜像可能更久。

### 6.3 构建失败怎么办

| 报错 | 原因 | 解决 |
| --- | --- | --- |
| `failed to resolve reference ... i/o timeout` | 拉不动 Docker Hub | 编辑 `docker-compose.1panel.yml`，把 `args.PYTHON_IMAGE` 改成 `docker.m.daocloud.io/library/python:3.12-slim` |
| `apt-get update` 卡住 | 国内访问 deb.debian.org 慢 | 同上，把 `args.APT_MIRROR` 改成 `https://mirrors.tuna.tsinghua.edu.cn` |
| `pip install` 超时 | 网络问题 | 确认 `args.PIP_INDEX_URL` 是清华源（默认已是） |
| `failed to read dockerfile` | 解压时漏了 `--strip-components=1` | 回到 3.2 重新解压 |
| `env file /opt/pa-agent/.env not found` | 还没建 `.env` | 回到第五节 |

### 6.4 启动后的目录结构

```bash
ls -la /opt/pa-agent/
drwxr-xr-x  config/         # settings.json / .runtime.lock
drwxr-xr-x  logs/           # pa_agent.log（轮转 5MB × 10）
drwxr-xr-x  trade_records/  # 交易记录 + auto_orders.jsonl
drwxr-xr-x  records/        # 每次分析的完整记录（pending/ 子目录）
```

这四个目录挂载进容器，**容器重建不丢数据**。

## 七、验证是否真的跑起来了

按顺序做，每步都有明确的「正常长什么样」。

### 7.1 容器在跑吗

```bash
sudo docker ps --filter name=pa-agent
```

正常：`STATUS` 列显示 `Up 30 seconds (healthy)` 或 `Up 2 minutes (health: starting)`。

`Restarting` → 看 7.2 的日志。

### 7.2 看启动日志

```bash
sudo docker logs pa-agent 2>&1 | head -40
```

**正常输出（关键三行）**：

```
2026-11-14 04:20:11 INFO pa_agent.daemon.config: 配置来源：data_source=settings symbol=settings ... fallbacks=3(settings) dingtalk=on
2026-11-14 04:20:11 INFO pa_agent.daemon.config: 守护进程启动：source=binance symbol=BTCUSDT tf=15m bars=100 poll=20s cooldown=120s wait_close=True auto_trade=off
2026-11-14 04:20:12 INFO pa_agent.daemon.runner: 分析引擎就绪（provider=glm-5）
```

三个关键点：

- **第二行「配置来源」** 告诉你每项配置究竟从哪来（`env` / `settings` / `default`）。
- `auto_trade=off` 说明当前是只分析模式。
- `分析引擎就绪（provider=xxx）` 说明 AI 客户端建好了。

### 7.3 自检

```bash
sudo docker exec pa-agent python -m pa_agent.daemon --health-check; echo "退出码: $?"
```

**退出码 0 = 健康**。会实际拉一次行情、检查 AI Key 与通知配置。

不健康的输出形如：

```
- AI API Key 未配置（provider.api_key）
- 行情自检失败：OKX 请求失败: https://www.okx.com: timed out —— 请检查网络或代理设置
```

### 7.4 等一次分析

如果 `PA_DAEMON_WAIT_BAR_CLOSE=true`，要等下一根 K 线收盘才会分析。想立刻验证：

```bash
sudo docker exec pa-agent python -m pa_agent.daemon --once
```

跑完会打印分析摘要，并在 `/opt/pa-agent/records/` 下生成一个 json。

### 7.5 看分析结果

```bash
sudo tail -f /opt/pa-agent/logs/pa_agent.log
```

匹配这些关键字：`stage1 done`、`stage2 done`、`决策`、`自动交易：`。

## 八、从「只分析」到「真实下单」

**这一步最容易出事，严格按顺序走，一档一档升。**

### 第 0 步：确认当前是完全关闭

```bash
grep -E "^PA_DAEMON_(AUTO_TRADE|DRY_RUN)" /opt/pa-agent/.env
# 应该是 AUTO_TRADE=false, DRY_RUN=true
```

### 第 1 步：只分析，观察 3~7 天

保持默认配置。每天看 `/opt/pa-agent/logs/pa_agent.log`，关注：

- 模型用的是哪个（有没有一直在降级）
- 决策方向是否合理（跟自己看图对比）
- 有没有反复出现 `余额不足` / `429` / `timed out`

### 第 2 步：开试运行（会记录「本应下单」，但**不发单**）

```bash
# 编辑 .env
PA_DAEMON_AUTO_TRADE=true
PA_DAEMON_DRY_RUN=true
```

改 `.env` **必须重建容器**（`docker restart` 不重读 `env_file`）：

```bash
cd /opt/pa-agent
sudo docker compose -f docker-compose.1panel.yml up -d --force-recreate
```

验证：日志里会出现

```
INFO pa_agent.trading.auto_trader: 自动交易：dry_run=True ... 
```

以及 `trade_records/auto_orders.jsonl` 里的 `"dry_run": true` 记录。

**观察 3~7 天**，看「本应下单」的决策质量。

### 第 3 步：交易所 Key 权限检查

| 交易所 | 检查项 |
| --- | --- |
| Binance | 勾「允许现货交易」；做合约再勾「允许合约交易」；IP 白名单含服务器公网 IP |
| OKX | 权限选「交易」；填 Passphrase；IP 白名单含服务器公网 IP |

### 第 4 步：先用模拟盘跑通真实链路

```bash
OKX_DEMO=true          # 或 BINANCE_TESTNET=true
PA_DAEMON_AUTO_TRADE=true
PA_DAEMON_DRY_RUN=false
```

重建容器，等一次真实成交。**必须复核**：

- 日志里 `保护单 3/3 条 ok`
- OKX / Binance 网页上：**持仓对数、条件单确实挂着**（止损 + TP1 + TP2）
- 钉钉收到成交回报

跑完记得清理：平仓 + 撤销条件单，确认 `持仓 0 / 挂单 0 / 条件单 0`。

### 第 5 步：小额度真单

```bash
OKX_DEMO=false
PA_DAEMON_AUTO_TRADE=true
PA_DAEMON_DRY_RUN=false
PA_DAEMON_MAX_NOTIONAL=15      # 先用 15 U，别贪
```

改完重建容器，看日志确认「单笔上限 15 USDT」。

> **安全兜底**：`.env` 里设 `PA_AGENT_FORCE_DRY_RUN=1` 可以强制所有下单走试运行，
> 无论配置怎么写。做测试 / 冒烟时打开它。

## 九、日常运维

### 9.1 看日志

```bash
# 实时跟踪
sudo docker logs -f --tail 50 pa-agent

# 文件版（含轮转，5MB × 10）
sudo tail -f /opt/pa-agent/logs/pa_agent.log

# 只看警告以上
sudo grep -E "WARNING|ERROR" /opt/pa-agent/logs/pa_agent.log | tail -30
```

### 9.2 健康状态

```bash
sudo docker inspect --format '{{.State.Health.Status}}' pa-agent
# healthy / unhealthy / starting
```

Docker 每 5 分钟自动跑一次 `--health-check`。连续 3 次失败标 `unhealthy`。

### 9.3 改配置的两种方式

| 改什么 | 怎么改 | 要不要重启 |
| --- | --- | --- |
| `.env`（AI Key、交易所 Key、杠杆、金额…） | 编辑后 `up -d --force-recreate` | **要**（`restart` 不行） |
| `config/settings.json`（5 个风控项、通知开关…） | 直接编辑保存 | **不用**，30 秒内热重载 |

热重载成功的日志：

```
INFO pa_agent.daemon.runner: 配置已热重载（settings.json）：模型 glm-5 → glm-5，杠杆 10 → 25，单笔上限 15.0 → 15.0 USDT
```

**注意**：`settings.json` 是 GUI 与守护进程**共享的唯一一份**。你在本机 GUI 里改参数、服务器上的 daemon 也有一份，两边可能互相覆盖 —— 这是 2026-11-14 加的乐观锁要解决的问题（写盘前校验文件指纹，不一致就拒绝写并提示）。

### 9.4 目录权限

镜像以 root 启动入口脚本，自动 `chown` 四个挂载目录到 UID 10001，然后降权运行。**不用手工改属主**。

如果宿主机上这些目录属于别的用户（比如 1000），在 `.env` 里改：

```
PA_AGENT_UID=1000
PA_AGENT_GID=1000
```

### 9.5 备份

```bash
# 最关键的是这三个
sudo tar -czf pa-agent-backup-$(date +%Y%m%d).tar.gz \
    -C /opt/pa-agent config trade_records records .env

# 存到别处
scp pa-agent-backup-*.tar.gz 你本机:/备份目录/
```

`settings.json` 有自动备份：每次覆盖前把上一个**能解析**的版本存成 `settings.json.bak`；文件损坏时自动恢复并保留损坏原件为 `settings.json.corrupt-<时间戳>`。

### 9.6 单实例锁

守护进程启动时会写 `/opt/pa-agent/config/.runtime.lock`，防止同一账户被两个实例重复下单。

**容器重建后会自动接管旧锁**（2026-11-14 修复）。如果日志还报：

```
RuntimeError: 已有 PA Agent 正在运行：daemon（pid=1，xxx，启动于 ...）
```

两种处理：

```bash
# 方案一：升级到最新版（新代码会自动接管陈旧锁）
# 方案二：手工删锁
sudo rm -f /opt/pa-agent/config/.runtime.lock
sudo docker compose -f docker-compose.1panel.yml up -d --force-recreate
```

应急开关（不推荐长期开）：`.env` 里加 `PA_AGENT_IGNORE_RUNTIME_LOCK=1`。

## 十、升级与回滚

### 10.1 升级

```bash
cd /opt/pa-agent

# 1) 备份（重要！）
sudo tar -czf ../pa-agent-before-upgrade-$(date +%Y%m%d).tar.gz \
    config trade_records records .env

# 2) 传新包上来并解压（覆盖代码，不动 config/）
sudo tar -xzf PA_Agent-server.beta.tar.gz --strip-components=1
sudo rm PA_Agent-server.beta.tar.gz

# 3) 重建镜像（--build 必须带）
sudo docker compose -f docker-compose.1panel.yml up -d --build --force-recreate

# 4) 验证
sudo docker logs pa-agent 2>&1 | head -20
sudo docker exec pa-agent python -m pa_agent.daemon --health-check
```

**`config/`、`logs/`、`trade_records/`、`records/` 不会被覆盖**（它们是宿主机目录，包里没有）。

### 10.2 回滚

```bash
cd /opt/pa-agent
sudo tar -xzf ../pa-agent-before-upgrade-20261114.tar.gz
sudo docker compose -f docker-compose.1panel.yml up -d --build --force-recreate
```

## 十一、定时运行窗口（省钱的用法）

只想在「18:00 到次日 08:00」运行？用 1Panel 的计划任务。

包里带了两个脚本：

- `deploy/cron-start.sh` —— 启动容器
- `deploy/cron-stop.sh` —— 停止容器（先 SIGTERM 让它收尾，30 秒后才强杀）

### 用法

1Panel → 计划任务 → 创建任务：

| 项 | 填法 |
| --- | --- |
| 任务类型 | Shell 脚本 |
| 执行周期 | 每天 18:00（启动）/ 每天 08:00（停止） |
| 容器 | **不勾选**「在容器中执行」—— 脚本要在宿主机跑 docker |
| 脚本内容 | `/bin/sh /opt/pa-agent/deploy/cron-start.sh` |

### 为什么不用 `docker compose down`

脚本用的是 `docker start` / `docker kill -s SIGTERM`，只操作 `pa-agent` 这一个容器：

- 不会重建容器（挂载与 env_file 在创建时已固化）
- 不会误动同机上别的服务
- 收到 SIGTERM 后守护进程会把当前分析收尾、写完整记录再退

## 十二、常见问题速查

### 启动类

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 容器 `Restarting`，日志报 `已有 PA Agent 正在运行` | 陈旧锁（旧版本缺陷） | 见 9.6 |
| `env file /opt/pa-agent/.env not found` | 没建 `.env` | 第五节 |
| `failed to resolve reference ... i/o timeout` | 拉了 Docker Hub 上不存在的镜像 | 必须用命令行 `--build`，见 6.1 |
| `failed to read dockerfile` | 解压漏了 `--strip-components=1` | 回 3.2 |
| `Permission denied` 写日志 | 挂载目录属主不对 | 设 `PA_AGENT_UID`/`PA_AGENT_GID`，见 9.4 |

### 分析类

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `AI API Key 未配置` | `.env` 没填或没重建 | 填 `PA_AGENT_API_KEY`，`--force-recreate` |
| `HTTP 400 code 1210` | bigmodel `max_tokens` 超 131072 | 不要手改 max_tokens，程序已自动限流 |
| `余额不足或无可用资源包` | AI 账户欠费 | 充值，或配 `PA_AGENT_FALLBACKS` |
| 分析一直不结束（几分钟无输出） | 模型网关慢，或走代理绕远 | 看 `stage1 done latency=`；配 `NO_PROXY` 让 AI 走直连 |
| `trade_confidence` 恒 50，下单全被拦 | 模型名写成了 `glm-4-flash` | 改回 `glm-5` |

### 交易类

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `50101 APIKey does not match current environment` | 实盘 Key 配了 `demo=true` | 模拟盘要单独申请 Key |
| `-2015 Invalid API-key, IP, or permissions` | IP 白名单没加服务器 IP | 交易所后台加白名单 |
| `50123 This API Key does not have trading permission` | 该交易对临时不可用（非全局） | 换品种试，或稍后再试 |
| 下单数量与预期差很多 | 张数按 `lotSz` 向下取整 | 正常，见 5.7 |
| 止损单挂着但数量是全量 | 旧版本缺陷 | 2026-11-14 已改用 `closeFraction=1` 全平语义 |

### 通知类

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 钉钉收不到 | Webhook/密钥错，或没重建 | 填 `DINGTALK_WEBHOOK_URL` + `DINGTALK_SECRET`，重建 |
| 收到信号但没收到成交回报 | 只分析 / 试运行 | 成交回报只在 `dry_run=false` 且真实成交时发 |
| `describe()` 显示 `dingtalk=off` 但实际在发 | 走的是环境变量兜底 | 已修，看真实配置用 `--health-check` |
