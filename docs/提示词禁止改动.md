# 提示词（`prompt_engineering/`）：**禁止改动 / 禁止精简**

> 本文件是硬性约束。任何「优化响应时间」「精简 token」「重构 prompt」的任务，
> **一律不得修改 `PA_Agent/prompt_engineering/` 下的任何文件**。

## 一、结论先写

| 事项 | 规定 |
| --- | --- |
| 修改 `prompt_engineering/` 下的 `.txt` | **禁止** |
| 「删掉不常用段落」「合并重复章节」 | **禁止** |
| 「用一个精简版替换 `市场诊断框架.txt`」 | **禁止** |
| 「把 K 线表压缩成摘要」降低输入 token | **禁止** |
| 「把 system prompt 两阶段合并/拆分以省 token」 | **禁止** |
| 新增 prompt 文件（会进包、影响判断） | 需用户明确同意 |
| 修错别字 / 改标点 / 调换段落顺序 | 视同改动，**禁止** |

原因：这些文件是交易判断的**唯一策略来源**，内容来自二元决策（Al Brooks 体系）的完整知识库。
任何删减都会直接改变模型的判断依据。响应时间慢是网络与 prompt 体量的问题，
**但体量本身不是可以拿去换速度的东西**——削 prompt = 削判断质量，属于产品决策，不是工程优化。

## 二、当时的原话（2026-11-11）

用户明确指示：

> 「prompt 本身目前不能优化缩小改动，请写入记忆 md，避免优化时不小心改动」

这条款适用于**所有**后续优化，包括但不限于：提升 AI 链路速度、降低 API 费用、
减少上下文占用、切换小模型、给免费池腾空间。

## 三、正确的优化方向（不动 prompt 的前提下）

响应时间的瓶颈在网络侧，prompt 拼装本身只有几毫秒。已经落地或可做的：

| 方向 | 状态 | 说明 |
| --- | --- | --- |
| 免费池按 prompt 体积预判跳过 | ✅ 已做（2026-11-11） | 实测单轮省 **66.2 秒**，见 `pa_agent/ai/sensenova_fallback.py` 的 `prompt_exceeds_free_window()` |
| OpenAI client 连接复用 | ✅ 已做（2026-11-11） | `DeepSeekClient._client_for()` |
| 方舟通道启用 KV 前缀链 | ⏸ 待定 | `supports_kv_prefix_chain()` 对 `doubao-*` 返 False，stage2 要重发全量 K 线表（7.4 万 token）。放开能省一半**输入**，但方舟是否真支持隐式前缀缓存未实测 |
| 减少免费池候选轮换次数 | ✅ 已做 | 截断即中止整段轮换（`aborted_by_truncation`） |
| 降低 429 退避上限 | ⏸ 可选 | `rate_limit.py` 现为 5/10/20/40/80 秒，最坏白等 155 秒；实测日志里没出现过 429，优先级低 |
| 增量分析（只发新增 K 线） | 已有能力 | `build_incremental_stage1()`，走 `analysis_mode` 相关开关 |

**注意**：上表里「省输入」的任何手段，都只能动**发送方式**（缓存、复用、增量），
不能动**内容本身**（不删段落、不缩写章节、不换更短的表述）。

## 五、唯一例外：对照上游仓库时发现 prompt 优化

**用户 2026-11-11 补充指示（原文 m10837）：**

> 「prompt 唯一改动的条件是我让你根据 https://github.com/rosemarycox5334-debug/PA_Agent
> 仓库对比时发现 prompt 进行优化才可以改动」

也就是说，**只有一条路**能改动 `prompt_engineering/`：

| 条件 | 是否满足才允许改 |
| --- | --- |
| 用户主动要求「对照上游仓库 `rosemarycox5334-debug/PA_Agent` 做同步/对比」 | ✅ 必须 |
| 对比过程中**发现上游对 prompt 做了优化**（新增策略文件、修正判断逻辑、补充知识库条目等） | ✅ 必须 |
| 用户**明确指示**把该优化移植过来 | ✅ 必须 |
| 「这样更快」/「这样省 token」/「我觉得这段啰嗦」 | ❌ 绝不构成理由 |
| 「顺手精简一下」/「合并重复章节」/「改个错别字」 | ❌ 绝不构成理由 |

### 移植上游 prompt 优化时必须做的事

1. **先报告再动手**：把上游改了哪个文件、改了什么（diff 摘要）、为什么算优化，先列给用户确认；
2. 用户点头后 **整文件覆盖**（或按 diff 精确移植），不做「顺手加料」；
3. 重跑真实两阶段分析（`.pipwork/run_e2e_timing.py`）确认判断仍成立；
4. 更新 `docs/prompt_baseline.json`（`total_bytes` 与对应文件的 sha256）与本文件第四节的指纹表；
5. 在 `部署完成说明.md` 的「上游同步记录」一节写明：上游 commit、改动文件、移植理由；
6. `python .pipwork/check_prompt.py` 此时会报 `PROMPT CHANGED`——这是**预期**的，但必须确认每一处改动都能对应到上游 commit，多出来的任何一处都是不合格。

### 除这条路以外

其余任何场景（性能优化、成本优化、代码重构、bug 修复、上游同步但上游没动 prompt）**一律不得改动 `prompt_engineering/`**。
